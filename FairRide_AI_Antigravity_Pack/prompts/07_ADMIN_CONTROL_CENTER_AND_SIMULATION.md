# Phase 07 — Admin Control Center and Dispatch Simulation Lab

## Objective
Create the judge-facing operational console and a reproducible comparison between nearest-driver baseline and FairRide multi-factor dispatch.

## Read first
`docs/04_DESIGN_SYSTEM.md`, `docs/05_UX_SCREEN_SPECIFICATION.md`, `docs/08_ALGORITHMS_AND_DEMAND_MODEL.md`, `docs/10_TESTING_AND_DEFINITION_OF_DONE.md`, `docs/11_DEMO_AND_SEED_DATA.md`.

## Admin Control Center
1. Build an information-dense operations layout with restrained navigation, status summaries, map, zone intelligence and recent event feed.
2. Include active rides, available drivers, completed rides, unassigned/exception rides and current zone pressure.
3. Add fleet map with meaningful marker states and a parallel accessible list/table.
4. Provide demand forecast versus actual by zone/time, with model version and synthetic-data badge.
5. Provide dispatch inspection with score breakdown and reason codes. Restrict access to authorized admins.
6. Add ride pool queue and exception queue with operational status and safe actions.
7. Metrics must be computed from persisted records or deterministic fixtures; do not insert arbitrary “impressive” KPI values.

## Simulation Lab
1. Add scenario controls for number of requests, supply level, zone distribution and demand profile. State the simulation seed.
2. Use one immutable generated input dataset for both algorithms in a run.
3. Run nearest-eligible-driver baseline and FairRide engine against the same candidate pool, constraints and requests.
4. Record average passenger wait, pickup ETA, idle-time distribution, workload inequality, completed/unassigned requests, utilization and empty pickup distance where measurable.
5. Show distributions and trade-offs, not just one headline score. Avoid claiming FairRide wins every metric.
6. Persist run configuration, input seed, algorithm versions and result metrics so the run can be reproduced.
7. Add export/download of a concise CSV/JSON run report if it can be completed without destabilizing the build.
8. Label this environment as a simulation, not live city operations.

## Design constraints
- No fake graphs, random metric animations, generic three-card layout repeated per section, gradients or glass surfaces.
- Use dense tables, clear headings, restrained status colors, direct labels and meaningful chart axes.
- Every chart must have loading, empty and failure states.

## Acceptance checks
- Non-admin users cannot access admin APIs or pages.
- Dashboard metrics reconcile with database query fixtures.
- A simulation run is deterministic for fixed seed and config.
- Both algorithms use identical input data.
- Results include enough information to explain any improvement or regression.
- All displayed simulation values are explicitly labelled.

## Report
Show screenshots or route names, metric definitions, one reproducible simulation configuration and a result comparison generated by the running code.
